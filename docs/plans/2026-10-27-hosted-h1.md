# Hosted Mode H1 (the MCP bus) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `yo-human-hosted`: one always-on Go service on Fly that holds the human's inbox, threads, answers and approvals, enforces the approval rules server-side, and exposes them as a remote MCP server to Claude in Duet (OAuth through GitHub, owner only) and to agents (per-node tokens scoped to a swarm), with quiet nudges to the owner's phone through the self-hosted Bark server from C1. Agents and spokes also use the bus to reach each other: they post to it and follow it by long-poll.

**Architecture:** A second binary in the same module, in its own tree, sharing no code with the CLI (spec, "Build order" 2):

```text
cmd/yo-human-hosted → internal/hosted/app (composition root: env config, subcommands)
                        ├→ internal/hosted/web    (inbound HTTP: MCP handler, tools, middleware)
                        ├→ internal/hosted/oauth  (inbound HTTP: the authorization server)
                        ├→ internal/hosted/nudge  (outbox worker; no network)
                        ├→ internal/hosted/notify (channel adapter interface: Level, Message, Channel)
                        ├→ internal/hosted/auth   (token minting, hashing, verification; no network)
                        ├→ internal/hosted/bus    (domain rules; standard library only)
                        ├→ internal/hosted/db     (SQLite; the single write path)
                        └→ internal/hosted/egress/{github,cimd,bark} (the only outbound network code)
```

`web`, `oauth`, `nudge` and `auth` depend on `bus` types. `db` implements `bus.Store`. Outbound calls happen only in `egress/*`, which import only the standard library and, for channels, `notify`. Bark is H1's only `notify.Channel`; H2 adds PagerDuty behind the same interface. Litestream runs as the container's supervisor and streams the database to Tigris.

**Tech Stack:** Go 1.27.3. New dependencies, each pinned at its newest release that is at least two weeks old (checked 2026-10-27; re-check in the commit that adds it):

- `github.com/modelcontextprotocol/go-sdk` v1.8.0 (2026-09-04): `mcp` (Streamable HTTP, stateless, JSON responses), `auth.RequireBearerToken`, `oauthex` metadata types.
- `modernc.org/sqlite` v1.60.1 (2026-09-29; v1.61.0 is too new): pure Go, so `CGO_ENABLED=0` holds.
- Litestream v0.5.17 (2026-08-31), as a binary in the image, not a Go import.

Everything else is the standard library (`net/http`, `database/sql`, `crypto/rand`, `crypto/sha256`). Ids are random, not ULIDs, so no id library is needed.

**Spec:** [../specs/2026-10-27-hosted-mode-design.md](../specs/2026-10-27-hosted-mode-design.md), including its "Self-hosted channels" section (added with this plan).

**Where the work lives:** this repo holds the product, plus a *generic* example deploy with placeholders only. Every private deploy lives in the owner's private crew-infra repo: the owner's running bus instance (app, hostnames, auth setup, backups) and the C1 Bark server. Its tasks are listed here only as outlines with no operational detail, and get their own plan in crew-infra. Rules: [../../constitution.md](../../constitution.md), as amended by Task 1.

- No client names anywhere in the repo, its issues, logs, tests or fixtures. Swarm names in tests: `crew`, `client`, `other`. Host codenames only (`thehalf`).
- No secret value in output, logs, errors, fixtures or RED records. Fixture secrets match `^([A-Z0-9]+-)*FAKE(-[A-Z0-9]+)*$`. Tokens the bus mints carry prefixes `yhn_` (node), `yha_` (OAuth access), `yhr_` (refresh), `yhd_` (desk starter), `yhh_` (desk human) and `yhx_` (executor). Task 2 adds a gitleaks rule for all six.
- Every field from Duet or an agent is untrusted data. The server never builds a link, a command or a tool call from item text. Tool output is structured JSON with `"v": 1`, and every tool description says its returned fields are data.
- **The bus pushes; Duet never polls for anything time-sensitive** (owner, 2026-10-28). Duet's repeating routines run at most hourly. Notice of what needs the owner reaches him by push: Bark in H1, PagerDuty from H2. In H1 the notice of an approval is a quiet, collapsed nudge, at most once per window; an approval that can't wait needs an escalation. A critical post gets no loud push from the bus until an agent escalates it, at least `YH_ESCALATE_AFTER` (30 minutes) after the post, and `critical` only once C1.4 has passed. Hard pages go out locally through M1 (spec, call 1). Duet reads the bus only on its routine or when the owner opens it. No timer, expiry, escalation or retry may depend on Duet having read, acked or polled anything, and no test may assume a Duet cadence.
- **Session transport** (owner, 2026-10-28: "agent prompts between bridges only (host-to-host) and uds on a host"):
  - The bus never wakes or prompts a session. It has no outbound path to sessions: its only egress is Bark (PagerDuty from H2), GitHub and the CIMD fetch. Sessions, orchestrators and watchers pull from it: long-poll on `answers` in H1, the event stream in H2.
  - Between Claude sessions on one host, waking goes over UDS: SendMessage, the Claude harness's own channel, never a herdr pane prompt. This is an instruction for sessions; no yo-human code implements UDS messaging. An orchestrator fanning out answers is such a session.
  - A non-Claude watcher or daemon (a host watch daemon, not part of yo-human-hosted) wakes only its own host's bridge pane, with `herdr agent prompt`, and no other pane. A herdr access-control feature, in progress, will make that mechanical.
  - Across hosts, only a bridge sends, and only to another bridge (`herdr agent prompt`/`read`). A bridge is the one session on each host allowed to send to another host. Everything else between hosts goes through the bus as items, threads and answers, so no other session prompts across hosts.
- **Reminders on a clock, not per event** (owner, 2026-10-28; protocol v1.2 §6).
  - The cap lives in the bus's delivery to the owner, not in each sender.
  - The same item reaches his phone at most once in 60 minutes, whatever its revision. That covers a collapsed nudge's count, a Duet post and an escalation (Task 11's `owner_pushes` ledger, checked by item).
  - A new revision may re-raise an item, but never sooner than 60 minutes after its last push. So re-posting every 30 minutes gives one push an hour, not two.
  - Only an escalation that passes Task 11b's gate goes sooner, under Task 11b's own per-item spacing.
  - Escalations are limited separately, per item and per swarm (Task 11b).
  - Outside the cap: desk pushes (owner-initiated, Task 10), hard pages (M1, and PagerDuty from H2), and H2's to-do digest, which names no item and runs on its own clock.
- **The bus moves no files** (owner, 2026-10-28). H1 has no attachment, upload, file or path field. Items carry capped text, and at most one `https` link to an allow-listed host: a pointer, never a copy. Bark pushes carry counts only. Any future file hand-off is a plan change, and it must meet all four of these:
  - (a) It never depends on an agent reading a protected Mac folder (Downloads, Desktop, Documents). Mac-side file work runs as its own launchd job with an explicit, documented TCC grant, or reads only from a dedicated drop folder outside the protected locations.
  - (b) It is owner-initiated and scoped. The destination is named per crew, and there is no general-purpose copy.
  - (c) It is visible and auditable: each hand-off is logged with size and sha256 only, never the contents.
  - (d) It keeps the client wall. A client's files go only to that crew's node, never through a repository, the shared bus database or a shared log.
- No real app names, hostnames, account ids or auth setup in this repo; those live in crew-infra. Fly work (crew-infra only) runs with `FLY_CONFIG_DIR` set to the owner's personal-org config. No deploy, public exposure, new secret or spend without the owner's go through the orchestrator. Read-only `fly` commands are fine.
- Size: two always-on machines in total, the bus and the C1 Bark server, about $4.18/month (math under C1); no further machine without the owner's go. Shared IPv4 only.
- Spec names, verbatim:
  - Duet tools: `inbox_for_claude`, `item`, `swarm_status`, `record_answer`, `record_approval`, `post`, `ack`
  - Agent tools: `post`, `answers`, `item`, `reply`, `status_push`, `escalate` (owner, 2026-10-27; Task 11b), `relay` (below)
  - Executor tools (its own principal kind `executor`, token `yhx_`, not crew-scoped, Task 10e): `approval_status`, `report_executed`, and `request_change` (Task 10f)
  - Desk tools: only under desk Option A (see "Human approval by passkey"): `item`, `record_answer` (answers only; a desk credential never resolves an approval)
- **Human approval by passkey (owner, 2026-10-27, from Duet; supersedes the human paths in #70):**
  - Every answer and approval row carries `actor_kind: human | agent`, derived **only** from the credential, never from the payload.
  - **Everything from Duet's connection is `agent`, always**, like a node token. Duet's `record_approval` stores the owner's quoted words and returns the approval page's link for Duet to send him; it **never** resolves.
  - **An approval resolves only on a fresh passkey assertion the owner makes himself** (Tasks 10c and 10d): any passkey with user verification (iCloud Keychain, 1Password, or a phone over the QR flow), on the bus's approval page. The WebAuthn challenge covers a hash of the exact payload he saw. Only a verified assertion produces `human`, for that one approval.
  - Questions and blockers (items with `action: none`) may be answered through Duet or by a node relay, recorded truthfully as `agent`. An answer to a question grants nothing; any item whose action isn't `none` must be an approval (Task 3), so a question can't carry one.
  - Nodes keep `relay` (stored as `agent`, never resolving).
  - Inbox groups: `approval`, `question`, `blocker`, `finished`, `failed`
  - Action categories: `merge`, `release`, `deploy`, `public-sync`, `force-push`, `delete`, `spend`, `secrets`, `money`. The owner's approval policy (decision 1, Task 10f) decides each one per target: `passkey`, `standing` or `deny`, and anything unlisted is `deny`. Only a `passkey` target can be posted as an approval. A `standing` action never reaches the bus; it runs under authority the owner has already delegated. `deploy` can't be `passkey` until agents run on the read-only Fly token (decision 3).
  - The never-list, `force-push`, `delete`, `spend`, `secrets` and `money`, is hard-coded `deny`. No policy can change it.
  - `YH_GATED_ACTIONS` is gone, folded into the policy file. The bus reads the same signed file and decides which items get a challenge. The executor enforces its own pinned copy and ignores the bus's.
- Limits (mechanisms, not policy):
  - handle ≤ 80 characters; title ≤ 200; summary ≤ 1000; detail ≤ 16 KiB; answer or approval text ≤ 4 KiB
  - risk flags ≤ 8, each `^[a-z0-9-]{1,40}$`; link ≤ 2048 bytes, `https` only, host in the link allow-list
  - request body ≤ 64 KiB; all text valid UTF-8, with control characters other than `\n` and `\t` refused
- Coordination with M1 (through the orchestrator): `go.mod`/`go.sum`, `.golangci.yml`, `Makefile`, `coverage-floors.json` and `perf-budgets.json` are shared with `feat/m1-notify`. Before each push, rebase on `origin/main` and re-run `make lint-rules-test`. Never touch the M1 worktrees or branches.

## Review Focus

1. **An approval recorded against a revision the human never saw.** Duet shows revision 1 while the agent re-posts revision 2, then Duet records the approval with `revision: 1`. Expected: rejected with `stale_revision`, nothing stored, and the error names the current revision. Pinned in Task 6 by `TestApprovalForOldRevisionIsRejected`.
2. **Two answers to the same question at once.** Expected: within one actor kind the first wins, and the others get `already_decided` with the winner's source and time (a byte-identical retry returns its own record). A `human` answer (desk, Option A) supersedes an `agent` one (Duet), and an `agent` answer after a `human` one is refused. Pinned in Task 6 by `TestConcurrentAnswersOneWins`, `TestHumanAnswerSupersedesAgent` and `TestAgentAfterHumanRefused`, on a real SQLite file.
3. **A swarm's token guessing another swarm's item id** (`item`, `reply`, `record_answer`, or an `answers` cursor). Expected: `not_found`, the same response as an id that doesn't exist, so a token can't tell a hidden item from a missing one. Pinned in Task 5 by `TestCrossSwarmIsIndistinguishableFromMissing`.
4. **Hostile item text:** instructions aimed at Duet, `javascript:`, `http:` or off-list links, a 20 KiB detail, invalid UTF-8, escape sequences, a `from` field claiming `duet`. Expected: links and limits refused with the field named, text kept verbatim as data, `from` taken only from the credential. Pinned in Task 3 by `TestDraftValidation` and in Task 5 by `TestFromComesFromCredential`.
5. **Someone other than the owner completing GitHub sign-in, or replaying a code.** Expected: a different GitHub user id gets no code, and its GitHub token is discarded. A second use of an authorization code fails and revokes every token issued from it. A reused refresh token revokes its whole family. Pinned in Task 10 by `TestNonOwnerGetsNoCode`, `TestCodeReuseRevokesFamily` and `TestRefreshReuseRevokesFamily`.
6. **An approval resolved by anything but the owner's own fresh passkey assertion**: Duet's `record_approval`, a replayed or expired assertion, one signed for another payload or revision, or one from another key. Expected: the item stays open every time. Pinned in Task 10c by the five tests the owner named, plus UV, origin and counter cases.
7. **A file passed through the bus**: an extra `attachment`, `file`, `path` or `content` argument on any tool, or a `link` of `file:///Users/…/Downloads/x.pdf`, a local path, or a `data:` URI. Expected: refused before any bus call, with nothing stored. No tool's input schema has a file-shaped property, so a file hand-off can't be added without a plan change that meets (a)-(d) in Global Constraints. Pinned in Task 9 by `TestNoFileHandOff` and `TestToolSchemasHaveNoFileFields`.

## Milestone C1: the self-hosted Bark server (crew-infra; outline here)

Owner decisions (2026-10-27):

- **Reaching the owner:** a self-hosted bark-server on Fly in his personal org, deployed from crew-infra. Bark's levels are `passive`, `active`, `timeSensitive` and `critical`. H1's quiet nudges go out as `active` by default (owner, 2026-10-27: a single `passive` nudge per window is too easy to miss), with `passive` configurable. An agent's escalation (Task 11b) can raise one item to `timeSensitive`, and to `critical` only once C1.4 has passed.
- **No private ntfy on Fly.** The homelab ntfy on thehalf stays as it is for homelab notifications; nothing here touches it. Moving crew pointers onto the bus comes later, with no rush.
- **PagerDuty** stays the backstop for hard pages (H2).
- **Session to session** goes through the bus: spokes and sessions post to it and follow it. H1 makes this first-class with long-poll on `answers` (Task 7). H2 adds an event stream for watchers that aren't MCP clients. Waking a session after a read follows the session-transport constraint: SendMessage between Claude sessions on a host, a non-Claude watcher prompting only its own host's bridge pane, and bridge to bridge across hosts.
- crewkit may use the Bark server later, as a second consumer.

**What the product side provides (this repo):** the `notify.Channel` adapter with a Bark implementation (Task 11), and a generic `deploy/example/` (Task 12). The Bark server needs nothing from yo-human's code.

**APNs:** bark-server sends to APNs (`api.push.apple.com:443`, HTTP/2) for topic `me.fin.bark`. It signs with the APNs token key that the official Bark app's maintainer ships inside bark-server, which is why the official App Store app works against a self-hosted server and why no Apple Developer account is needed. Verified in bark-server v2.3.9's source (2026-10-27); re-check on every image bump. The detailed C1 plan lives in crew-infra. Owner steps:

1. Install Bark and add the server URL with its credentials.
2. Allow notifications and Critical Alerts when iOS asks.

  - `func Parse(b []byte) (Policy, error)`: strict JSON (unknown fields refused), `v: 1`. It refuses a rule naming a never-list action or an action outside the category list. Keys must be spelled exactly and appear once per object (encoding/json folds case and keeps the last duplicate). Each pattern uses the real targets' alphabet plus `*`: `repo` is `owner/name` (the owner not starting with `-`, no `.git` suffix in any case); `merge`, `release` and `public-sync` rules need a `ref` and no `env`, `deploy` rules an `env` and no `ref`; a `ref` pattern may not start with `refs/`, and may use `*` only once, as its last character (every mode). Patterns are capped at the targets' limits: repo 200, ref 100, env 63.
  - `func (p Policy) Decide(a string, t Target) Mode`: the never-list is checked first and returns `deny`. Otherwise, over every rule whose action is equal and whose `repo`, `ref` and `env` patterns all match, precedence is independent of file order: `deny` beats `passkey`, which beats `standing`. No match returns `deny`. Matching is a glob where `*` matches any run of characters, `/` included, for every field: ref `*` covers `release/1.2`, so a deny-all on `*` can't be dodged by a rule on `release/*`. For `repo` only, the pattern and the value are both case-folded; refs are case-sensitive, so a deny on `v*` doesn't cover `V1.0`. An empty pattern matches only an empty value.
  - `func (p Policy) Gates() ([]Rule, error)`: the `passkey` rules that win for at least one target, for the rulesets of decision 2. Each rule's witness (its patterns with `*` replaced by a private-use rune no pattern contains) makes `Gates` and `Decide` agree; over the real targets' smaller alphabet a gate can be over-listed, the safe side.
  - `func (p Policy) Shadowed() ([]Rule, error)`: the rules that never win (for example, a `standing` rule fully covered by a `passkey` one), which `policy gates` prints as warnings. Both return `ErrNoWitness` when no rune in U+E000-U+F8FF is free (only a hand-built policy), never a guess.
  - `func RulesetRefPatterns(action, ref string) []string`: the full-ref ruleset patterns that cover exactly what the ref pattern matches. GitHub documents ruleset matching as Ruby `File.fnmatch` with `FNM_PATHNAME`, where `*` and a bare `**` stop at `/` and only `**/` crosses it, so a trailing-`*` pattern `pre*` becomes the pair `pre*` and `pre*/**/*`, under `refs/heads/` for `merge`, `refs/tags/` for `release`, and both for `public-sync`. `testdata/fnmatch.tsv` (Ruby-generated) checks it row by row. If GitHub folds case the rulesets cover a superset, otherwise exactly the same set. `policy gates` (Task 10f) emits it, and the executor's ruleset check (Task 10e) compares with it.
  - `func TargetFor(action, repo, ref, baseRef, target string) Target`: the one mapping, used by the bus and by every executor wrapper. `merge` → `{repo, baseRef, ""}`; `release` → `{repo, ref (the tag), ""}`; `public-sync` → `{repo, ref, ""}`; `deploy` → `{repo, "", target (the environment)}`.

### Human approval by passkey: design (owner, 2026-10-27; revised after the review of 124d7b3)

**Terminology (owner, 2026-10-27): "crew" replaces "swarm".** A crew can span machines (the Mac, cloud and homelab nodes in one crew), and its tokens and the payload binding belong to the crew, not to one host, so a crew's nodes on several machines share its scope. This section uses `crew` (the payload field is `crew`). Renaming the merged text (Global Constraints, Tasks 3 to 9, Task 13, the spec) is a follow-up PR; until then "swarm" there means the same thing. The follow-up also renames `Item.Swarm` (the payload's source) and `Draft`/test references, and the test crews (`crew` and `client` become, for example, `main` and `client`), so the example name doesn't collide with the term.

**WebAuthn itself, not an identity provider.** The target is a signature over the exact approval, and that needs the challenge under our own control. Pocket ID with OIDC `max_age=0` proves only a fresh login, not what was approved, and would add a third always-on app. H1 implements WebAuthn with `github.com/go-webauthn/webauthn` v0.18.2 (2026-09-19, the newest release at least two weeks old). It's allowed in exactly one package, `internal/hosted/approval`, which the bus and the executor share (Task 10c).

**Authenticators (owner, 2026-10-27).** His words: "if we can have it somehow where my passkey confirms these things. on a screen not holding the key the qr method is great (scan qr with my phone), or if the keychain has the passkey (e.g. 1password)".

- Any passkey with user verification: iCloud Keychain, 1Password, or a phone over the QR flow.
- `authenticatorAttachment` is unset at registration and at assertion, so platform authenticators (Touch ID, Face ID), passkey providers, and the hybrid flow on a screen that doesn't hold the key all work.
- `userVerification: "required"` everywhere; the UV flag is checked at the bus and again at the executor. `attestation: "none"`.
- Up to 5 credentials (for example iCloud Keychain plus 1Password). Adding one is gated by an existing passkey (Task 10d).
- The WebAuthn user handle is 32 random bytes, never the GitHub id.

**The payload** (`approval.Payload`, Task 10c), with `v: 1` and these fields, every key always present (an empty string, never omitted):

`purpose` (`"approve"`), `item`, `kind`, `handle`, `action`, `repo`, `ref`, `base_ref`, `target`, `pinned_commit`, `pinned_tree`, `revision`, `decision`, `crew`, `requester`, `content_hash`, `expires_at`.

- `repo`, `ref`, `base_ref` and `pinned_tree` are real `Draft` fields (Task 3).
- `content_hash` is SHA-256 over the canonical full `Draft`, which covers everything the page renders (summary, risk flags, link included).
- `expires_at` is the challenge's expiry (Unix seconds), so it's signed.
- The encoding is RFC 8785 (JCS) canonical JSON, UTF-8. Every value is a string or an integer: no floats, no nulls.
- `challenge = SHA-256(nonce ‖ SHA-256(JCS(payload)))`, with a 32-byte random `nonce`. The bundle carries the payload, the nonce and the assertion, so anyone holding the pinned keys can check it offline.

**The page and the ceremony.** `GET /approve/<item>?rev=<n>` on the bus.

- **The page:**
  - It renders the bus's own copy, never values from the URL: handle, kind, action, repo, ref, base, target, pinned commit and tree in full, revision, crew, requester, summary, risk flags, and the link as text.
  - Every field is escaped as text.
  - Open it in Safari or another full browser. The Claude app's in-app browser is checked in the live drill only.
  - Anyone with the link can read the item; that risk is accepted and stated. The link grants nothing.
- **The ceremony:**
  1. The page asks `POST /approve/challenge` with `{item, rev, decision}`. The bus builds the payload from its current copy, stores `{challenge, nonce, payload JCS, payload_hash, item, revision, expires}`, and returns the challenge, `allowCredentials` (the owner's credentials) and `userVerification: required`.
  2. Then `POST /approve/assert`, all in one transaction:
     1. take and delete the challenge (single use);
     2. check the expiry;
     3. verify the assertion with `approval.Verify`;
     4. recompute the payload from the item and require its hash to equal the stored one;
     5. call `RecordApproval` with the challenge's revision and payload hash, which recomputes both inside the same transaction.
- **What `approval.Verify` checks:**
  - the signature, against the stored credential;
  - `rpIdHash == SHA-256(YH_WEBAUTHN_RP_ID)`;
  - `origin == YH_APPROVE_ORIGIN` exactly;
  - `type == "webauthn.get"`;
  - no `crossOrigin: true` and no `topOrigin`;
  - the user-present and user-verified flags both set;
  - the user handle equal to the credential's;
  - the credential id in `allowCredentials`.
- Only `passkey` targets ever get a challenge. No cookie or session exists: one approval, one fresh assertion.

**RP ID and origin.** The RP ID is the page's exact host (`approve.example.com` in this repo; the real one is in crew-infra), never the registrable parent domain. So no other host under that domain, Bark included, can ask for an assertion on this credential. The origin is `https://` plus that host, compared exactly. Routing is by host and by listener (Task 9): the approval host serves only `/approve*`, `/passkey/*` and their static files, 404 for everything else; the MCP host refuses `/approve*` and `/passkey/*`. The approval host is the only one on the platform's public port. The MCP host listens on loopback and is reached only through the tunnel, so the MCP host's name sent straight to the app's public IPs gets 404, and so do approval routes sent through the tunnel. The approval host's DNS carries a CAA record limited to Fly's CA. That guards only against certificates from other CAs: a zone editor can change it, and `accounturi` is used only if Fly publishes a per-customer account URI (Fly's ACME account may be shared). Against a zone editor the controls are DNS-change alerts delivered outside the zone admin's control, the challenge-time push, and a registrar or zone lock with the owner as the only zone editor (crew-infra).

**The sign counter.**

- A new counter is accepted when it's greater than the stored one, or when both are 0. Synced passkeys (iCloud Keychain, 1Password) always report 0.
- Refused, with a synchronous Bark alert: `stored > 0 && new <= stored`, or the library's `CloneWarning` set.
- The backup-eligible flag is fixed at registration, and a change is refused.
- The executor keeps no counter: for synced keys it adds nothing.

**The challenge store.**

- 5-minute TTL (`YH_CHALLENGE_TTL`, at most 10), single use.
- At most 3 open per item and 20 overall. At the cap, the oldest is evicted instead of refusing, so an agent holding challenges open can't lock the owner out.
- A per-IP limit of 10 challenges a minute. Expired rows are purged on every write.

**Page headers.** `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, plus:

- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Cross-Origin-Opener-Policy: same-origin`
- `Referrer-Policy: no-referrer`
- `Cache-Control: no-store`
- `Permissions-Policy: publickey-credentials-get=(self)`, and on the enrolment page `publickey-credentials-create=(self)` too

POSTs need `Content-Type: application/json` and `Origin == YH_APPROVE_ORIGIN`. The script is a static file; there's no inline script.

**On his phone.** The synced passkey signs with Face ID in Safari; a screen without the key uses the QR flow. Both are in the live drill.

**Desk: two options, for the owner.**

- **Option A, keep #70's desk sign-in, answers only:** the device flow, the `yhd_` starter, the `yhh_` token and the keychain client (Tasks 10's desk part and 10b) answer questions. Its keychain runner (`security -i`) lives in its own binary, `cmd/yo-human-desk`, since `internal-no-exec` forbids `os/exec` under `internal/`. They never resolve an approval (constitution VIII); the desk tools are `item` and `record_answer`.
- **Option B, recommended:** `yo-human-desk approve <item>` prints the approval page's URL to open in a browser, and Touch ID on the Mac signs the same payload. It needs no `os/exec`. Under Option A as well, B's page is the only way to approve at the desk.

    - A row whose item was pushed less than 60 minutes ago, at any revision, is held, never dropped: its `next_at` moves to that push plus 60 minutes.
    - When held `duet_post` rows for one item come due together, they coalesce into one push. It carries the newest post's title and summary plus `(+<n> more)`, and the others become `superseded`. Its Bark `id` is `yh-<lowest outbox id in the group>`, stable across retries and re-sends.

    - An escalation that passed Task 11b's gate bypasses the per-item cap. It has its own per-item and per-swarm limits there.

    - Broken (401 or 403): the row stays `pending`. The worker sets the sticky `delivery_broken` state (since, status) and stops the pass.
