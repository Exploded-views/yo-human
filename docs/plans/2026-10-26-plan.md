Every milestone: test-first with RED recorded, coverage and perf ratchets in CI, docs (inputs-first, DRY), a review before merge, an independent security-minded review for anything touching secrets, inbound replies or plugin isolation.

## M0: Decide and scaffold (owner + 1 session)
- Owner answers OPEN-QUESTIONS.md (at least 1, 2, 4).
- Pick language and runtime and record why (a single static binary suits a CLI plus daemon; bitc and memsync are Go).
- Repo scaffolding: CI on hosted runners, workflow lint (copy crewkit's `tools/check-workflows.py` pinned by sha256), coverage and perf ratchet files, SECURITY.md, CONTRIBUTING.md, CODEOWNERS.

## M1: Core and outbound notify (v1 part 1)
- Data model: message (level, title, body, project, agent, needs-answer, dedup key), delivery, question, rule, context; a durable local store with atomic writes.
- CLI: `yo-human notify|resolve|status` with documented exit codes; enqueue locally in milliseconds and deliver asynchronously (the agent never waits on the network).
- Delivery daemon with retries and backoff, delivery state, and a dead-letter view.
- Channels (built in for v1, behind the plugin interface): PagerDuty (Events v2: trigger, ack, resolve with dedup; urgency mapping), ntfy, and a local log channel for tests.
- A drop-in shim for an existing page script (Q7).
- Tests: a fake PagerDuty, a fake ntfy, a fake clock; perf budget on `notify` (p95 tens of ms).

## M2: Ask and question sessions (v1 part 2)
- `yo-human ask` creates a question (context, options, importance, asker); `yo-human wait <id>` returns the answer with bitc-style exit codes (answered; still waiting; expired; cancelled).
- Question sessions through herdr: a dedicated, named, short-lived session holding the question, Blocked until answered, so Heeler pushes it; the answer is captured and relayed to the asker; the session closes. Nothing ever types into a session yo-human didn't start.
- The answer path is channel-neutral underneath, so channel-native replies plug in later.
- Escalation engine: per rule, an unanswered question escalates on a schedule to other channels (for example to PagerDuty after N minutes). Mechanism only; the user sets policy.
- Tests: a fake herdr API, a fake clock for escalation, end-to-end "ask → answer → asker resumes".

## M3: Living, conversational rules and context
- A rule and context model: scoped (project, agent, level), optional expiry, "back" signals (said so, expiry, activity).
- Agent-facing commands to read, propose and write rules (`yo-human rule add|list|expire`), with validation and a dry-run "what would happen to this message now?".
- A setup conversation, as a skill: the agent interviews the user, proposes defaults with reasons, writes rules; no hard-coded preferences.
- Quiet hours, do-not-disturb and break-through rules.

## M4: Channel plugin SDK and isolation
- The manifest (`yo-human.channel.json`), closed capability set, small interface, core-owned correlation IDs (see docs/research/2026-10-26-plugin-models.md).
- Plugins out of process with only their own secrets and an outbound-host allowlist; pinned versions and checksums; an Apprise-style URL shorthand; a quality tier per channel feeding the router.
- Move the built-in channels onto the SDK; first external channels later (Twilio SMS and voice, chat apps).

## M5: Agent integration
- An MCP server over the same core; a skill (when to notify vs ask vs escalate, levels, exit codes) with before-and-after evals; a crewkit plugin that installs it.

## Parallel track U: Heeler upstream and fork sync
- Install the Claude GitHub App on the fork; write the guarded daily sync job (summary issue plus sync PR, never merges).
- Upstream PRs, one problem each: agent-authored messages with levels through the plugin and relay; time-sensitive interruption level; notification actions; reply from notification. Raise the Critical Alerts entitlement with the maintainer.

## Rough sizing (agent hours, test-first; excludes waits)
M0 2–3 h, M1 8–12 h, M2 10–14 h, M3 6–9 h, M4 8–12 h, M5 4–6 h, U ongoing. v1 = M0–M2.
